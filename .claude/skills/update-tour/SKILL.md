# Update the system tour

Brings [SYSTEM_TOUR.md](../../../docs/overview/SYSTEM_TOUR.md) back in line with its sources, then regenerates `docs/overview/system-tour.html` from it. The Markdown is a derived view: when it disagrees with a source, the source wins. The HTML is generated from the Markdown only.

Doc rules this skill relies on (read them; they are not repeated here): [docs/README](../../../docs/README.md) (frontmatter, open questions), [GLOSSARY](../../../docs/GLOSSARY.md), [R-DOC-01 to R-DOC-03](../../../docs/RULES_AND_CONSTRAINTS.md#r-doc-01), [R-TEST-01](../../../docs/RULES_AND_CONSTRAINTS.md#r-test-01) (docs-only Definition of Done), [R-REPO-04](../../../docs/RULES_AND_CONSTRAINTS.md#r-repo-04) (no new dependency).

## Stop and ask when

- Two sources disagree on a fact the tour shows → STOP. Name both and ask ([CLAUDE.md §6](../../../CLAUDE.md#6-when-unsure)).
- A flow cannot be drawn without a step, an order or a value that no source gives → do not invent it. Draw only what the sources give, mark the gap with ❓Q-xx; if no Q-ID covers the gap, STOP and propose one.
- A change would need a new source in `derived_from` → ask first.

## Content rules (MUST)

1. **Sources only.** The only sources are the `derived_from` list in the tour's frontmatter. Every statement comes from one of them. Each section ends with `Sources:` and relative links.
2. **Nothing invented.** No fact, rule, number, feature, step, step order, state, arrow or example that the sources do not give. A Recommendation in [OPEN_QUESTIONS](../../../docs/OPEN_QUESTIONS.md) is not a decision: never draw or state it as an answer. If a flow follows a list that a question only proposes, say so and mark that Q-ID.
3. **Status** of every feature, step and box:
   | Status | Rule | Flowchart | Sequence diagram |
   |---|---|---|---|
   | Core | Stated by the README. An epic whose Scope is "README" is Core | solid, class `core` | solid arrow |
   | Proposed | A detail an epic adds beyond the README text, or an epic whose Scope is "new scope proposal" (Decision `_pending_`) | dashed, class `proposed`, label names EP-xx | dotted arrow `-->>`, label starts with EP-xx |
   | Accepted | An epic whose Decision is `accepted` or `changed` | solid thick, class `accepted`, "EP-xx" | solid arrow + "EP-xx" |
   | Undecided | An open question blocks it | ❓Q-xx on the exact box, arrow or step; class `decision` only when the step itself may not exist | ❓Q-xx in the label or a note on that step |
4. **Markers.** A ❓Q-xx sits on the exact step, arrow or box the question affects, and links to `../OPEN_QUESTIONS.md#q-xx` (in text; under each diagram, a "❓ in this diagram:" line with the links). Options are drawn as a branch labelled with the Q-ID, never as the answer. Every Q-ID used is `open` in OPEN_QUESTIONS; a merged one is replaced by its target.
5. **Terms.** GLOSSARY terms exactly; never a "DO NOT use" word as its qualifier forbids it (check every hit). Roles are `Buyer`, `Seller` and `Admin`; describe the Admin team as EPICS does. Explain each GLOSSARY term in plain words at its first use in the file, not later.
6. **Plain English** everywhere in the Markdown (R-DOC-03).

## What the tour contains

Section 0 is the status legend (the table in rule 3). Then, each with `Sources:`:
1. **The system in 5 minutes:** what TallyMart is, who uses it, how money and goods move, why the two core invariants matter. Explain each invariant with the example its own source gives.
2. **Big picture:** actors, the 10 contexts, external providers, and the arrows the README diagram draws. About 20 nodes at most.
3. **Role guides,** one per role, benefits first: a feature table (feature | epic | status | ❓), a journey flowchart from first use to the role's end goal built only from that role's features in the sources, and a "Decisions that affect …" line.
4. **Core flows** as `sequenceDiagram`s, with steps taken from the sources: the Checkout saga; the money flow (Ledger entries from Payment to Withdrawal); Shipment and successful delivery; and one small diagram per failure case in the [README: The problem](../../../README.md#the-problem) table that the tour lists.
5. **Order state machine:** only the states the sources name; the rest marked with Q-IDs.
6. **Feature catalogue:** every epic in [EPICS](../../../docs/product/EPICS.md): epic | for whom (its Benefits line) | context | priority | status | Q-IDs.
7. **Decisions waiting for you:** generated by the script (step 4). Never copy options or analysis.

Diagram rules: Mermaid only; one idea per diagram, about 15 to 20 nodes; every flowchart declares the four `classDef`s; every diagram has a 1 to 3 sentence explanation under it. So that Presentation mode can hide markers cleanly: put a question about a box on its own `<br/>` line; separate label parts with " · "; when a note only makes sense with its question, write it as one segment (", so …", not " · ").

## Steps

1. Read every source in `derived_from`, in full. Find what changed since the tour's `last_verified`: `git log --since=<last_verified> -p -- <sources>`.
2. Update the Markdown. Keep anchors (`<a id="sN">`) stable. Set `last_verified` to today.
3. Grep the file for every GLOSSARY "DO NOT use" word and judge each hit.
4. Run, from the repo root:
   ```
   python3 -I .claude/skills/update-tour/build_tour.py decisions   # rewrite section 7
   python3 -I .claude/skills/update-tour/build_tour.py check       # must print 0 problems
   ```
5. Run the [`/audit-docs`](../audit-docs/SKILL.md) step 4b checks on the tour against `derived_from`, as three independent reviewers (A rules and decisions, B facts and terms, C epics and questions). Write the report to `.claude/reviews/`. Fix what the sources settle; report the rest.
6. Generate the HTML. `<scratch>` is a scratch folder outside the repo (the Vietnamese JSON MUST NOT be committed, R-DOC-03):
   ```
   python3 -I .claude/skills/update-tour/build_tour.py units --vi <scratch>/vi.json
   # fill every null value with Vietnamese (rules below)
   python3 -I .claude/skills/update-tour/build_tour.py build --vi <scratch>/vi.json
   ```
   `units` reuses translations already in the HTML, so only new or changed units are null. Translation rules: same meaning, nothing added; keep GLOSSARY terms, IDs (R-…, Q-xx, EP-xx), code, provider names, status and priority words, and every link URL in English; in a diagram translate label text only, never IDs, arrows or line count.
7. Test in local headless Chrome (no install). Add `--dump-dom` to print results:
   ```
   "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --allow-file-access-from-files \
     --user-data-dir=<scratch>/chrome --virtual-time-budget=120000 --dump-dom \
     "file://$PWD/.claude/skills/update-tour/browser_test.html?t=file://$PWD/docs/overview/system-tour.html"
   ```
   Pass: in all four modes (EN, VI, each with and without Presentation) `errors=0` and `text-leaks=0`; with Presentation on, `with-markers=0`; `anchors missing: 0`; both marker clicks land on a `#d-q-xx` row. Then add `&dump=en` and `&dump=vi` and read the Presentation text: no sentence may point at something hidden.
8. If a diagram's shape (its step order or its states) is itself undecided, add its key to `INTERNAL_ONLY` in `build_tour.py`: Presentation mode then hides the whole diagram instead of showing an undecided shape as fact. Keys are `<section anchor>#<n>`; update them when diagrams move.
9. Report: what changed and from which source, the review findings left for the owner, the Q-IDs added or removed, and the test results. Docs-only Definition of Done: R-TEST-01.

## What Presentation mode hides (built into `build_tour.py`)

The intro before section 0; sections 0 and 7; table rows whose status is Proposed or Undecided; ❓ and Q-ID columns; every sentence or list item that names a Q-ID, an EP-ID, "proposed", "not decided", "dashed", "amber", "solid", `_pending_` or "Sources:"; in diagrams, proposed and `decision` boxes, dotted arrows, marker segments and question lines, and the diagrams in `INTERNAL_ONLY`.
